# Research: risen-spass as test harness and infrastructure donor

Source: `B:\DevDrive\git\github\risen-spass` (MIT, read-only for us; commit `bad2534` at the time of writing). These notes
cover what a Vulkan replacement renderer for Risen Enhanced x64 can reuse: the loading chain, the hook/symbol
infrastructure, everything spass already knows about rendering, the Lua test tooling, gaps, the headless Ghidra workflow
and the build conventions. Paths in `src/...`, `docs/...`, `scripts/...` are relative to the spass repo unless noted.

Status markers: **[read]** = read in spass source/docs, **[measured]** = checked on this machine during this research
(read-only: imports of the test copy's binaries, export lists), **[inferred]** = our conclusion, not verified in the game.

## 1. Loading chain

### 1.1 How spass gets in [read]

* `Risen.exe` statically imports `sentry.dll` (Sentry-native crash reporter). spass builds a DLL named `sentry.dll`
  (`spass_proxy` target, `OUTPUT_NAME sentry`) whose 169 exports are linker forwarders to the renamed original
  `sentry_orig.dll` (`src/proxy/sentry_proxy.def`, generated by `tools/gen_proxy_def.py`; an import lib
  `sentry_orig.lib` is generated from `src/proxy/sentry_orig.def` with `lib /DEF:` because MSVC needs one for
  `name = module.name` forwarders). No game binary is modified. Install: `scripts/install.ps1` renames the original.
* `DllMain(DLL_PROCESS_ATTACH)` (`src/proxy/dllmain.cpp`) -> `spass::onProcessAttach` (`src/bootstrap.cpp`), under the
  loader lock, on the main thread, before `main()`:
  1. paths, log (`bin\spass\spass.log`), `bin\spass\config.toml`, crash handler (vectored handler + top-level filter,
     minidumps), trace channels, test settings;
  2. `hooks::initialize()` (MinHook), `crash::installHooks()`;
  3. `game::resolveSymbols()` - first pass: Engine/Game/FFC/SharedBase are already **mapped** (static imports of the exe),
     Script.dll is not (it comes with `Script_Game.dll`, loaded by `gCScriptAdmin::PostInitialize`);
  4. optional `CreateMutexA/W` rename (`[debug] instance`), `SHGetFolderPath*` redirect (`[debug] app_data`), file trace;
  5. `game::installHooks()` + `hooks::enableAll()`: `gCScriptAdmin::PostInitialize`, `gCSession::Process` (`tick`),
     `eCApplication::DoRender` (`ui.frame`), loc hooks, event hooks, template hooks, engine guards, file trace, mod mount.
* Lua starts in the detour of `gCScriptAdmin::PostInitialize` (second symbol pass, script hooks, `onGameReady()`).
  Measured by spass (DEVELOPMENT.md "Startup time"): PostInitialize returns at ~19.5 s, first `tick` ~25.6 s,
  `session.start(new)` ~29.3 s. ~13 s of the start is spent in the **AMD D3D9 driver** (shader cache), i.e. the D3D9
  device exists long before Lua runs.

### 1.2 Startup sequence of the engine relative to D3D9 [read RE.md section 2 + measured exports]

`Risen.exe` main (RVA `0x1290`): `gCGameApp` ctor -> compilers -> Steam -> command line -> splash ->
**`eCApplication::Create(hInstance, configName, cmdline)`** (window, engine, modules; this is where the graphics
subsystem and the D3D9 device are created) -> `LoadProjectFile` -> `GotoStartPosition`, `PlayIntros`, `StartGame` ->
`eCApplication::Run` (main loop).

### 1.3 Does spass load native plugins / extra DLLs? [read]

**No.** There is no plugin loader, no `LoadLibrary` of user DLLs, no C ABI for native extensions. The only
`LoadLibrary` calls are `dbghelp.dll` (crash), `shell32.dll` (folder redirect) and `d3d9.dll` (screenshot dummy device).
Indirect routes that exist:

* `[lua] unsafe = true` (`test-run.ps1 -Unsafe`) gives mods `ffi`, `package`, `io`, `os`: a test mod can
  `ffi.load("B:/.../reg_testapi.dll")` or call exported C functions of an already loaded DLL via `ffi.C`/`ffi.load("d3d9")`.
  This is **too late** to influence device creation (Lua starts ~19 s in), but it is a zero-change way for spass test
  scenarios to drive our renderer (toggle debug views, read GPU timings, request a Vulkan-side capture).

### 1.4 Would a `bin\d3d9.dll` proxy conflict with anything? [inferred from the code]

* **Not with spass's loading**: spass is `sentry.dll`, we would be `d3d9.dll`; both are loaded by the OS loader.
* **spass screenshot**: `findPresent()` does `LoadLibraryW(L"d3d9.dll")` -> gets **our** module (already loaded by base
  name), calls our `Direct3DCreate9`, creates a throw-away device on a hidden 64x64 window and hooks vtable slot 17
  (`Present`) of whatever device object we return with MinHook. Then `capture()` calls `GetBackBuffer`,
  `CreateOffscreenPlainSurface(D3DPOOL_SYSTEMMEM)`, `GetRenderTargetData`, `LockRect`, expects `X8R8G8B8`/`A8R8G8B8`.
  => If we wrap/implement the D3D9 API, either implement those calls correctly (and tolerate a second device on a
  hidden window), or provide our own capture (preferred, see 5) and avoid `risen.debug.screenshot`.
* **Two MinHook instances**: spass links MinHook statically; `hooks::enableAll()` uses `MH_ALL_HOOKS` of *its own*
  instance only, so it does not touch our hooks. Hooking the **same** target from both instances works (MinHook relocates
  a leading `jmp rel32`) but un-hooking order matters. Avoid hooking what spass hooks: `eCApplication::DoRender`,
  `gCSession::Process`, `gCScriptAdmin::PostInitialize`, `IDirect3DDevice9::Present` (on demand), `CreateMutexA/W`,
  `OpenMutexA/W`, `SHGetFolderPathA`/`SHGetSpecialFolderPathA`, the crash-reporter hooks, file-open trace, VFS mount.
* **Crash handler**: spass's vectored handler + top-level filter will also report crashes inside our DLL
  (`Module+RVA` banner in `bin\spass\crash.log`, minidump with `[debug] crash_dump = "mini"`). Useful, not a conflict.
  `guarded()` (SEH) around engine calls only covers spass's own calls.
* **Folder redirect**: with `[debug] app_data` set, `SHGetFolderPathA(CSIDL_LOCAL_APPDATA)` returns the test copy's
  `localappdata\Local`; if our renderer stores a pipeline cache / config under `%LOCALAPPDATA%` via that API it will land
  in the test copy too (good for isolation).
* **Users' DXVK / ReShade** already use `bin\d3d9.dll`: our proxy would collide with them (document it; optionally
  chain-load a `d3d9_chain.dll`).
* `d3dx9_39.dll` will still be called by Engine.dll for effects/sprites/shader assembly against whatever device we hand
  out: if we replace the D3D9 API entirely, D3DX must keep working on our device objects (it calls back into the
  device's vtable), which is a strong argument **against** implementing a full fake D3D9 and **for** intercepting at
  the engine level (`eCGfx*`/`eCDX9*`/`eCRenderSystemAdmin`).

### 1.5 Options to get our code running before the D3D9 device is created

| Option | How | Pros | Cons |
|---|---|---|---|
| A. `bin\d3d9.dll` proxy (recommended for standalone) | export `Direct3DCreate9` (+ forward `Direct3DCreate9Ex`, `D3DPERF_*`, `Direct3DShaderValidatorCreate9`, ... to `System32\d3d9.dll`). Do nothing heavy in `DllMain`; on the **first `Direct3DCreate9` call** (main thread, after all DllMains, inside `eCApplication::Create`) install engine hooks by decorated name. | Independent of spass; loaded automatically because Engine.dll imports d3d9; earliest point where Engine.dll is initialised and the device does not exist yet. | Collides with DXVK/ReShade; spass screenshot then talks to our module. |
| B. `bin\d3dx9_39.dll` proxy | same idea for the other static import of Engine.dll | no collision with DXVK/ReShade | 100+ D3DX exports to forward; odd. |
| C. Hook from our own `DllMain` | MinHook `eCApplication::CreateGraphicsSubsystem` (`0x4c4330`) or `eCDX9Instance::CreateDevice` (`0x74b2b0`) | earliest | Our DLL (as Engine's dependency) runs DllMain **before Engine.dll is initialised**: GetProcAddress on Engine works but calling Engine code there must be avoided. Prefer A's lazy init. |
| D. Small spass addition: `[native] load = ["reg.dll"]` | spass's DllMain hooks `eCApplication::CreateGraphicsSubsystem` and `LoadLibraryW`s the listed DLLs in the detour (outside the loader lock, before the device), then calls an optional `extern "C" void spass_native_init(const SpassNativeApi*)` | one injector for everything; plugins could get access to spass's symbol table, log, and register Lua functions | needs a spass change; ties renderer to spass for players |
| E. Lua `ffi.load` (unsafe) | from a test mod | no spass change | too late for device creation; dev-only |

Recommended: **A** for the shipping renderer (works with or without spass), plus **E** (or **D** later) so spass test
scenarios can talk to the renderer through a tiny `extern "C"` test API exported from our DLL.

## 2. Hook infrastructure [read]

### 2.1 `src/hook/` (~160 lines, deps: MinHook, spdlog)

* `hook_manager.h/.cpp`: `hooks::initialize()` (`MH_Initialize`), `shutdown()`, `create(name, target, detour, &orig)`
  (`MH_CreateHook`, logs), `enableAll()` (`MH_EnableHook(MH_ALL_HOOKS)`). All hooks are created disabled and enabled
  together so no half-installed state is visible.
* `template <class Fn> class Hook { Fn original; bool install(name, Fn target, Fn detour); bool installed(); }`.
  Usage: `static Hook<void(*)(void*, bool)> g_appRender; g_appRender.install("eCApplication::DoRender", s.app_do_render, &detour);`
* `exports.h/.cpp`: `exports::resolve(module, symbol)` = `GetModuleHandleW` + `GetProcAddress` (never loads a library;
  safe under the loader lock), `resolveAs<Fn>()`, `moduleBase(module)` for RVA fallbacks.

### 2.2 `src/game/symbols.h` X-macro table

```cpp
#define SPASS_SYMBOLS(X) \
    X(field, L"Module.dll", "?Decorated@Name@@...", ReturnT (*)(Args...), required) \
    ...
#define SPASS_DECLARE(field, module, name, type, required) std::type_identity_t<type> field = nullptr;
struct Symbols { SPASS_SYMBOLS(SPASS_DECLARE) };
const Symbols& sym();
std::vector<std::string> resolveSymbols();   // resolves every not-yet-resolved symbol whose module is loaded; returns missing required ones
```

* `resolveSymbols()` (`symbols.cpp`) is incremental: run at DllMain and again when late modules (Script.dll) appear.
  Optional symbols (`required = false`) only disable their feature; `risen.engine.missing()` lists them at run time.
* Already present render-adjacent entries: `app_instance` (`?GetInstance@eCApplication@@SAAEAV1@XZ`),
  `app_current_camera`, `app_do_render`, `cam_get_position/view/fov/aspect` (see 3.3), `phys_*` ray tests.
* Lookup lists: `%TEMP%\risen_re\<Dll>.exports.txt` (decorated) and `<Dll>.demangled.txt` (`RVA ordinal signature`),
  generated by `tools/dump_exports.py` (pefile with `max_symbol_exports` raised: Engine has 14 836 exports) and
  `tools/demangle_exports.py`. `docs/SYMBOLS.md` is generated by `tools/gen_symbols_doc.py`.
* Gotcha (CLAUDE.md): if a header is replaced by a file copy with an old mtime, MSBuild may skip dependants and the
  `Symbols` struct layout differs between TUs (silent breakage): `touch` it.

### 2.3 `src/game/abi.h` - MSVC x64 conventions (RE.md section 6)

* `this` is the first argument; a non-trivially-copyable class returned by value (`bCString`, `bCVector`, `bCMatrix`,
  `Entity`) comes back through a hidden pointer (RCX for statics, RDX after `this` for members), callee constructs,
  caller destroys. A non-trivial class passed **by value** is a pointer to a caller-made copy that the **callee destroys**.
* `BString` (owning `bCString`, 8 bytes, ctor/dtor via SharedBase exports `??0bCString@@QEAA@PEBD@Z`,
  `??1bCString@@QEAA@XZ`, `?GetText@bCString@@QEBAPEBDXZ`), `ByValueString` (no dtor: callee destroys), `OutString`
  (hidden-return slot, `take()`), `UString`/`OutUString` (`bCUnicodeString`), `EntityHolder` (Script.dll `Entity` = one
  `eCEntity*`).
* `guarded(lambda)` -> `invokeGuarded` (`abi.cpp`): runs under SEH `__try/__except`, returns false on an access violation,
  records `file:line` in the crash breadcrumbs.
* Maths types: `bCVector` = 3 floats; `bCMatrix` = 16 floats, row-major, row 0 right, row 1 up, row 2 forward,
  row 3 position, +y up, left-handed (RE.md section 50).

### 2.4 Share or copy?

**Copy** (with attribution, MIT): `src/hook/*` (4 files), the X-macro pattern from `symbols.h/.cpp` (our own table),
`abi.h/.cpp` (only `BString`/`guarded`), `src/common/crash.*` if wanted, `tools/dump_exports.py`,
`tools/demangle_exports.py`, `tools/pe_info.py`, `tools/disasm.py`, `tools/ghidra/*.java`.
Reasons: the code is tiny and stable; spass is a large repo (LuaJIT, sol2, modkit with imgui/glfw, pack2mod) with no
library target that exports only the hook layer (`spass_core` is everything); a submodule would drag its vcpkg manifest
along; `abi.h` depends on spass's `sym()` table layout. If both projects keep growing the same primitives, extract a
small header-only `risen-abi` repo later (hook wrapper + exports + bCString + guarded + bCMatrix/bCVector).

## 3. Rendering-related knowledge in spass

### 3.1 `src/game/screenshot.cpp` - `risen.debug.screenshot` [read]

* OS capture (`PrintWindow`, `BitBlt`, `CopyFromScreen`) of the D3D9 window returns **black** (RE.md sections 13, 42).
* On the first request: `findPresent()` creates `Direct3DCreate9(D3D_SDK_VERSION)` + a windowed
  `D3DCREATE_SOFTWARE_VERTEXPROCESSING | D3DCREATE_DISABLE_DRIVER_MANAGEMENT` device on a hidden `SpassDummyD3D` window,
  reads vtable slot **17** (`IDirect3DDevice9::Present`, shared by every device of that d3d9.dll), releases it, and
  MinHooks `Present`. The detour drains the pending requests and for each: `GetBackBuffer(0,0,MONO)` ->
  `CreateOffscreenPlainSurface(SYSTEMMEM)` -> `GetRenderTargetData` -> `LockRect` -> BGRA->RGB -> PNG with stored
  (uncompressed) deflate blocks (~4 MB at 1600x900) -> `<bin>\spass\screenshots\<name>.png`.
* Captured **before** the original `Present`, i.e. the finished back buffer including the GUI.
* Limits: multisampled back buffer fails (`GetRenderTargetData`), fullscreen may fail (dummy device), only 32-bit BGRA.
* **Bug found**: the `wait_frames` argument is stored (`Request::wait`) but **never used** - every pending request is
  captured at the very next `Present`. Scenarios work around it with time-based waits (`wait_s(...)` before `shot`).
* `screenshot_status(name)`: `"pending" | "done" | "failed: <reason>" | nil`.

### 3.2 Per-frame hooks [read]

* `tick`: detour of `gCSession::Process` (Game.dll `?Process@gCSession@@UEAAXXZ`, RVA `0x9711e0`), after the original;
  only while a session runs and the world is not paused (~80 per second regardless of resolution or `<Timer>` keys).
* `ui.frame`: detour of `eCApplication::DoRender(bool)` (Engine `0x4c0d40`), emitted **before** the original; runs once
  per main-loop pass, also at the title screen, while loading and while a menu pauses the world. When there was no
  session tick and a menu is browsing, spass also pumps `risen.test` waits from here.

### 3.3 Camera [read RE.md section 38, symbols.h]

* `eCApplication::GetInstance()` (static, `ms_pApplication` at `0xc62568`), `GetCurrentCamera()` (`this+0x38`, else
  `this+0xc8`) -> `eCCameraBase`: **view matrix at `+0x10`** (`GetViewMatrix`), position `+0x90`, FOV `+0xd4` in
  **radians** (1.0472 = 60 deg; axis assumed vertical, not proven), `GetAspectRatio` = **height/width** (0.5625).
* View direction = third **column** of the row-major view matrix `(m[2], m[6], m[10])`; `GetZAxis` returns a row and is
  not the view direction. World is left-handed, +y up, units ~cm, yaw 0 looks along +z, 90 along +x.
* Lua: `risen.world.camera()` -> `{x,y,z, dx,dy,dz, fov(deg), aspect}`.
* Unbound but exported (useful for us): `eCCameraBase::GetProjectionMatrix` (`0x80b90`), `GetWorldToScreenMatrix`
  (`0x4f5480`), `SetViewMatrix` (`0x80b30`), `SetProjectionMatrix` (`0x80ba0`), `SetPosition`, `SetRotation`,
  `SetFieldOfView`, `SetClipDepth`; `eCApplication::SetCurrentCamera/SetMainCamera/GetMainCamera`,
  `RenderAndDrawTo(HWND, const eCCameraBase&, bool)` (`0x4c1620`), `DrawTo(HWND, const eCCameraBase&)`.
* Game.dll `gCCameraAdmin` (94 exports) has the engine's own **free-fly and fixed cameras**:
  `OnToggleFreeFlyCam` (`0x7ac530`), `OnToggleFixedCam` (`0x7ac520`), `SetFixCamera(const bCMatrix&, ...)`
  (`0x7a8630`/`0x7a8940`), `StopFixCamera` (`0x7a8460`), `IsFixCameraActive`, `SetFreeCamSpeed/FOV/TurnSpeedFactor`,
  `SetDebugMode`, `SetCurrentCameraByName`, `SetCameraFOV`. spass notes (RE.md section 46) that the debug-camera
  *actions* are not in this build's key table, so these would have to be called directly (how to reach the
  `gCCameraAdmin` instance is not documented: probably a module via `eCModuleAdmin::FindModule`).
  Script.dll: `Entity::GetCameraPose`, `Entity::SetCurrentCameraByName`, `Entity::SaveCameraDump`.

### 3.5 Window, resolution, fullscreen [read]

* Windowed: `data\ini\ConfigLocal.xml` `<Window FullScreen="false" ... Right="1280" Bottom="720">` (test copy has it);
  `%LOCALAPPDATA%\Risen\ConfigUser.xml` `<Window Right/Bottom>` overrides the size and **the game rewrites that file**.
  `test-run.ps1 -WindowSize 1600x900` writes it before the start. **Never resize the window at run time** (GUI and mouse
  misalign). GUI virtual resolution is 1365x768 scaled to the window (`eCGuiModule2 +0x20/+0x24`).
* `Risen.exe -res=640x360` is accepted (no speed gain measured), `-nosplash` is always passed by `run-windowed.ps1`.
* Single-instance mutex `GenomeMutex` (SharedBase `g_CreateMutex`, RVA `0xa9100`); `[debug] instance` renames it.

### 3.6 Data formats relevant to a renderer (RE.md sections 26, 49, 53, 54, 56)

* Resources are found by bare compiled name in a name cache (`X._xmsh`, `._xmat`, `._ximg`, `._xmac`); loose files in
  mounted dirs work; `risen.assets.resource(name)` returns load state 0..3.
* `._xmsh` (section 53): sub-meshes with a **D3D9 vertex declaration** (`D3DVERTEXELEMENT9` list up to `D3DDECL_END`),
  vertex/index data, index format `D3DFMT_INDEX32`=102/`INDEX16`=101; the static vertex is 52 bytes (position, normal,
  tangent, two D3DCOLORs, one UV), V is `1 - v` of modelling tools; **front faces are clockwise** (D3D culls CCW).
  risen-modkit writes byte-identical meshes (`src/modkit/core/` mesh writer, `modkit_tests meshwrite_reproduces_a_shipped_mesh`).
* `._ximg` (section 49/53): header with `Width`/`Height`/`SkipMips`/`PixelFormat` (`eEColorFormat` = D3DFORMAT: 21
  A8R8G8B8, DXT1/3/5) + an ordinary DDS payload.
* `._xmac` actors (section 54) read offline by the modkit (102/111 actors give a visible mesh); materials: STDMATERIAL
  layers with map type 2 diffuse, 5 normal, 3 specular.
* Entity flags `eCEntity +0x28`: `0x2` rendering, `0x4` enabled, ...; `Entity:enable_rendering(false)`.
* Offline readers in spass: `tools/g3pak.py` (G3V0 archives), `g3tple.py`, `g3tab.py`; C++ in `src/modkit/core/`
  (`genome.*`, `image.cpp`, `imagelist.*`, mesh/actor readers).

### 3.7 Visual-verification experience (RE.md section 46)

The Extended-Mod work used `mods/extmod_shots` to compare screenshots with and without a mod (brightness of dungeons,
textures, meshes). Follow camera responds to actions `ZoomIn`, `ZoomOut`, `TurnLeft`, `TurnRight`, `ResetCamera`,
`LookBack` via `risen.input.simulate`. `Entity:set_frozen(true)` turns an entity into an ice statue (do not use for
looks), `enable_rendering(false)` hides it. Frame-to-frame differences exist even in a static scene (wind, animation).

## 4. Testing tools for a renderer

### 4.1 Lua API (exact names; `types/risen.d.lua` is authoritative)

Screenshots / debug:

### 4.3 Scenario: teleport to N locations, wait for streaming, screenshot, exit

Pattern taken from `mods/meshprobe_shots/main.lua` and `mods/extmod_shots/main.lua` (both verified in spass):

```lua
-- mods/render_shots/main.lua   (mod.toml: id = "render_shots", name = "...", version = "1.0.0")
-- .\scripts\test-run.ps1 -Mods render_shots -WaitForResult -Seconds 300 -Scenario render_shots -Param tag=vk
local T = risen.test
local tag = T.param("tag", "d3d9")
local SPOTS = {                       -- x, y, z, yaw (engine units ~cm, +y up, yaw 0 = +z); or { entity = "<unique name>" }
    { name = "beach",  x = 0, y = 0, z = 0, yaw = 90 },   -- fill with real coordinates (risen.entity.player():pose())
    -- ...
}
T.plan { "spots" }

local function wait_s(s)
    local t0 = T.elapsed()
    T.wait_until(function() return T.elapsed() - t0 >= s end, s + 15, "wait " .. s .. " s")
end
local function shot(name)
    local ok, why = risen.debug.screenshot(name)
    if not ok then return false, why end
    T.wait_until(function() return risen.debug.screenshot_status(name) ~= "pending" end, 20, "screenshot " .. name)
    return risen.debug.screenshot_status(name) == "done"
end

T.run(function()
    T.wait_event("session.start", 240, function(m) return m == "new" end)
    wait_s(2)
    pcall(risen.gui.close, 26)          -- the "Press START" page left open by the test start
    wait_s(25)                          -- the new-game intro / camera fly-in
    risen.world.set_time(12, 0)
    local p = risen.entity.player()
    local done = 0
    for i, s in ipairs(SPOTS) do
        T.section(s.name)
        local ok
        if s.entity then ok = p:teleport(s.entity) else ok = p:set_pose { x = s.x, y = s.y, z = s.z, yaw = s.yaw } end
        T.expect("teleport " .. s.name, ok)
        wait_s(8)                       -- streaming: no "loaded" signal exists (gap 5)
        risen.input.simulate("ResetCamera", true); wait_s(0.3); risen.input.simulate("ResetCamera", false)
        wait_s(2)
        if shot(("%s_%02d_%s"):format(tag, i, s.name)) then done = done + 1 end
    end
    T.expect("spots", done == #SPOTS, done .. "/" .. #SPOTS)
end)                                    -- T.run calls T.finish(); with [test] enabled the process exits
```

Notes: `y` should come from the terrain (`risen.world.trace` straight down, or `risen.world.nav_point`), otherwise the
player falls or sticks; time-based waits are needed because `wait_frames` is ignored; for reproducible A/B comparisons
use the same window size, time and spot order, and expect small differences from wind/animation.

Steps to decompile an Engine.dll function by RVA:

1. Find the RVA: grep `%TEMP%\risen_re\Engine.demangled.txt` (format `RVA ordinal signature`, RVA hex without `0x`),
   e.g. `eCApplication::CreateGraphicsSubsystem` -> `004c4330`. Regenerate missing lists with
   `python tools/dump_exports.py %TEMP%\risen_re <dlls...>` + `python tools/demangle_exports.py`. Image base of every DLL
   is `0x180000000`; `FUN_1804c4330` in a dump = RVA `0x4c4330`.
2. Run (PowerShell, timeout 600000 ms; well under a minute once the project opens; the script **appends**):

```powershell
$env:JAVA_HOME = 'C:\Users\johnh\scoop\apps\openjdk21\current'; $env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
$out = 'B:\DevDrive\risen-ghidra\reg_gfxinit_dump.txt'; Remove-Item $out -ErrorAction SilentlyContinue
& B:\D\ghidra_12.0_PUBLIC\support\analyzeHeadless.bat B:\DevDrive\risen-ghidra\Engine RisenEngine `
  -process Engine.dll -noanalysis -readOnly `
  -scriptPath B:\DevDrive\git\github\risen-enhanced-graphics\tools\ghidra `
  -postScript DumpDecomp.java $out 0x4c4330 0x74b2b0 name:eCDX9Instance::Init strref:"Direct3DCreate9" 2>&1 | Select-Object -Last 5
```

   Specs: `0x<RVA>` (function containing it), `name:<substring>` (max 20 matches), `strref:<substring>` (functions
   referencing a defined string). One DLL per invocation.
3. Read the dump with Read (`offset`/`limit`) or Grep `^// ` headers: each function has entry, RVA, signature, up to 12
   callers, then the C. Run again with the RVAs of `FUN_...` callees as needed.
4. Other scripts: `Callers.java` (all code refs to functions), `DataInit.java` (who initialises a global), 
   `DumpVtable.java <rva|sym:Class::vftable>:<count>` (vtable slots -> RVAs) - essential for `eCDX9Device`/`eCGfx*`

5. Reading rules: MSVC x64 conventions (2.3); vtable calls appear as `(*(code**)(*p + 0x178))(...)`; enums get
   mis-typed; say what is read vs inferred; record RVAs/offsets in our `docs/RE.md`.
6. **Lock contention**: spass sessions use the same projects; "Unable to lock project" = another headless run or GUI has
   it open: wait. Keep dumps outside the repo (`B:\DevDrive\risen-ghidra\reg_*.txt`) to avoid clobbering spass's.
